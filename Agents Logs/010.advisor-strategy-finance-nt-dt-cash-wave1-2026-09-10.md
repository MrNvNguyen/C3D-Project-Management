## Challenged assumption

**Team assumption:** “Wave 0 Q1 green + wiring `IN ('pending')` or SQL `SUM(amount/(1+vat_pct/100))` closes P0; Wave 1 DoD in the plan (HSPL + estimate-vs-actual + costs + executive + dashboard) can be claimed from those SQL edits.”

**Counter:**

1. `amountExcludingVat` / `computeBookedRevenue` use **`Math.round`**. SQL float `amount/(1+vat/100)` **will drift** from the locked 1.1tr fixture. Wave 1 NT/GTTT **must** load payment rows (`status, amount, paid_amount, vat_pct`) and call `aggregateThreeMoney` (or `amountExcludingVat` per row). Do not invent a second VAT strip in SQL.
2. Adding `pending` to `payment_status IN (...)` **without** changing the date predicate **does not** include pending booked: `syncPaymentToRevenue` sets `revenue_date = null` for pending. Every **period-scoped** W1 booked sum (dashboard YTD, costs-*) must treat pending via `payment_requests.request_date` (join `revenue_id`). Lifetime executive dashboard booked has no date trap — status include is enough.
3. Plan Wave 1 **close** names HSPL + estimate-vs-actual. Those surfaces are already before-VAT / pending-in-booked (C6; HSPL list uses `enrichPaymentMetrics`). Touching them is Wave 2/3. Wave 1 **cannot** claim `same_three_numbers_across_surfaces` including analytics. Q1 vitest **cannot** close W1 money.
4. `pending_revenue` on costs-* stays a **cash-sense** leftover (pending NT **before VAT**, period by `request_date` on period endpoints). It must **not** be subtracted from `revenue.value`. Do not expand it to partial unpaid remainder in this wave.
